## 🧠 Context

`maatify/data-repository` هي مكتبة **Infrastructure-level** تُستخدم في طبقات أعلى (Services / Application / API).
في هذا المستوى، **Logging وObservability** يجب أن يكونوا:

* واضحين في الحدود
* غير متطفلين
* لا يفرضوا سياسات تشغيل
* لا يُحوّلوا المكتبة إلى Monitoring Framework

ظهرت اقتراحات لإضافة:

* Query logging افتراضي
* Timing / metrics داخل كل operation
* Automatic slow-query detection

لكن هذه الاقتراحات قد تؤدي إلى **تجاوز النطاق** وكسر الفصل بين Infrastructure وApplication concerns.

---

## ❗ Problem Statement

بدون حدود واضحة للـ Logging وObservability:

* المكتبة قد تفرض logging strategy على المستهلك
* تتسرّب تفاصيل حساسة (queries / params)
* تتعقّد الاختبارات
* يُضاف overhead غير مرغوب
* يتحول Repository إلى نقطة مراقبة مركزية (anti-pattern)

نحتاج إلى **حدود صارمة**: ماذا تسجّل المكتبة؟ وماذا لا تسجّل؟

---

## ✅ Decision

### 1️⃣ **No Mandatory Logging**

`maatify/data-repository`:

* ❌ لا تقوم بتسجيل logs افتراضيًا
* ❌ لا تطبع output
* ❌ لا تفرض Logger implementation

أي logging هو **اختياري وصريح** فقط.

---

### 2️⃣ **PSR-3 Is Optional & Passive**

إذا تم دعم logging:

* يكون عبر `Psr\Log\LoggerInterface` فقط
* يُحقن صراحة (constructor / setter)
* عدم وجود logger:

    * لا يُغيّر السلوك
    * لا ينتج warnings
    * لا ينتج noop objects مخفية

---

### 3️⃣ **Logging Is Observational, Not Operational**

المكتبة قد تُسجّل (اختياريًا):

* High-level events فقط:

    * Operation started / failed
    * Safety guard triggered
    * Configuration errors

❌ ممنوع تسجيل:

* SQL queries كاملة
* Query parameters
* Raw dataset contents
* Hydrated objects

تفاصيل التنفيذ **ليست من مسؤولية المكتبة**.

---

### 4️⃣ **Exceptions Are the Primary Signal**

المكتبة تعتمد على:

* Exceptions (ADR-012)
* Typed error flow

Logging **لا يُستخدم** كبديل عن:

* Exception
* return values
* control flow

---

### 5️⃣ **No Metrics, No Timers, No Counters**

المكتبة **لا توفّر**:

* Performance metrics
* Query timings
* Counters
* Histograms
* Tracing spans

هذه المسؤوليات تقع على:

* Application layer
* APM tools
* Infrastructure monitoring

---

### 6️⃣ **Observability via Integration, Not Ownership**

المسموح:

* Integration hooks (اختياري)
* Event dispatchers خارجية (إن وُجدت)
* Decorators / proxies في التطبيق

المرفوض:

* Embedded observability systems
* Automatic instrumentation
* Hidden telemetry

---

### 7️⃣ **Testing & Logging Separation**

* Fake Adapters لا تعتمد على logging
* Tests لا تتحقق من log output
* لا يوجد coupling بين behavior وlogging

أي test يعتمد على log output هو **test خاطئ**.

---

## 🔧 Mandatory Implementation Requirements

هذا الـ ADR يفرض:

1. إزالة أي logging افتراضي
2. جعل Logger اختياري وصريح
3. منع تسجيل البيانات الحساسة
4. عدم إدخال metrics أو timers
5. توثيق حدود logging بوضوح في README

---

## ❌ Explicitly Rejected Alternatives

تم رفض ما يلي:

* Automatic query logging
* Slow query detection داخل المكتبة
* Built-in metrics collectors
* Logging كوسيلة تحكم
* Environment-based logging toggles

هذه الأساليب تُكسر الفصل المعماري.

---

## 🏁 Consequences

### ✅ Positive

* مكتبة خفيفة ونظيفة
* لا تفرض سياسات تشغيل
* اختبارات أبسط
* DX أوضح
* مرونة أعلى للتكامل الخارجي

### ⚠️ Trade-offs

* لا يوجد observability out-of-the-box
* يتطلب إعداد إضافي من التطبيق

هذه التضحيات **مقصودة ومقبولة** لمكتبة Infrastructure.

---

## 📌 Final Note

Logging وObservability في `maatify/data-repository`:

* **اختياري**
* **Passive**
* **غير تدخلي**
* **محدود النطاق**
* **لا يمتلك القرار التشغيلي**

هذا القرار **مغلق** لكل إصدارات v1.x.
