# 📜 Architecture Decision Record (ADR)

## ADR-001 — DataRepository Scope Lock & Refinement Strategy

**Status:** ✅ Accepted
**Date:** 2025-12-19
**Project:** `maatify/data-repository`
**Decision Owner:** Maatify Architecture
**Applies To:** v1.x (current major line)

---

## 🧠 Context

`Maatify DataRepository` is a strict, type-safe data access abstraction designed to unify interaction with multiple storage engines (MySQL, MongoDB, Redis) through a consistent repository API.

During extensive internal and external reviews, multiple expert assessments were collected focusing on:

* Architecture quality
* Performance and scalability
* Redis behavior
* Type safety and static analysis
* Developer experience (DX)
* Open Source adoption risks

The reviews consistently confirmed that the **overall architectural direction is correct**, but identified **specific high-risk areas** that require refinement to ensure long-term stability and correct usage expectations.

---

## ❗ Problem Statement

Without explicit architectural decisions:

* Redis repositories risk unsafe usage patterns (blocking commands, memory exhaustion)
* Consumers may incorrectly expect ORM or Query Builder capabilities
* Interface contracts are broader than necessary
* Minor SQL inconsistencies could cause production failures
* Future contributions risk expanding scope unintentionally

A clear, locked decision is required to:

* Prevent scope creep
* Protect performance and safety
* Preserve the library’s core value proposition

---

## ✅ Decision

### 1️⃣ **No Rewrite, No v2 Migration**

* The library **will not be rewritten**
* No ORM, Query Builder, or Query DSL will be introduced in v1.x
* Architectural direction is **validated and locked**

---

### 2️⃣ **Explicit Scope Lock**

This library is **NOT**:

* An ORM
* A Query Builder
* A Redis search engine
* A relationship mapper
* A transaction orchestration system

This library **IS**:

* A repository abstraction layer
* Adapter-driven and storage-agnostic
* CRUD + simple filtering + pagination
* Type-safe and static-analysis–first
* Hydration-pipeline–driven

---

### 3️⃣ **Redis Is a Special Case (Non-Relational)**

Redis repositories are explicitly scoped as:

* Key-value / cache-oriented repositories
* Suitable for **small or indexed datasets only**
* **Not** equivalent to MySQL or Mongo repositories

Mandatory constraints:

* Blocking commands (`KEYS *`) are forbidden
* SCAN-based iteration is required
* In-memory filtering must be limited or guarded
* Unsafe usage must throw warnings or exceptions

---

### 4️⃣ **Interface Segregation Is Required**

The repository contract will be split to respect ISP:

* `ReadRepositoryInterface`
* `WriteRepositoryInterface`
* `RepositoryInterface` extends both

This allows:

* Read-only repositories
* Cleaner type-hinting
* No “unsupported operation” exceptions

---

### 5️⃣ **Strict Mode Is Non-Negotiable**

The following are **locked decisions**:

* PHP `declare(strict_types=1)`
* PHPStan Level Max compliance
* `@template T` generics
* 5-stage hydration lifecycle
* DTO-based pagination results

---

## 🔧 Immediate Action Items (Derived)

This ADR mandates the following refinements:

1. Redis performance and safety fixes (SCAN, limits, guards)
2. SQL identifier quoting consistency in MySQL repositories
3. Interface segregation implementation
4. Scope documentation (README / SCOPE.md)
5. Minimal safety-focused test coverage

---

## ❌ Explicitly Rejected Alternatives

The following were reviewed and rejected for v1.x:

* Fluent Query Builders
* ORM-style relations or joins
* Query optimizers or planners
* Redis relational abstractions
* Implicit magic behavior beyond documented scope

These may only exist in **separate libraries with distinct scopes**.

---

## 🏁 Consequences

### Positive

* Clear identity and boundaries
* Reduced misuse and unrealistic expectations
* Safer Redis usage
* Easier long-term maintenance
* Strong OSS positioning

### Trade-offs

* No advanced querying features
* Redis behavior is intentionally limited
* Consumers requiring ORM features must use other tools

These trade-offs are **intentional and accepted**.

---

## 📌 Final Note

This ADR **closes all architectural debates** related to scope, Redis behavior, and feature direction for `maatify/data-repository` v1.x.

Future discussions must start from this document.
