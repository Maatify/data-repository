## 🧠 Context

`maatify/data-repository` مصممة لتكون **Infrastructure-safe** وقابلة للاختبار بدون الحاجة إلى:

* قواعد بيانات حقيقية
* Docker
* Services خارجية
* Network access

لتحقيق ذلك، تعتمد المكتبة على **Fake Adapters** تحاكي السلوك الوظيفي (Behavior) وليس التنفيذ الداخلي (Implementation).

ظهرت تساؤلات حول:

* مدى دقة هذه الـ Fakes
* هل يجب أن تحاكي الأداء؟
* هل يجب أن تكون بديلة كاملة للـ Drivers الحقيقية؟

---

## ❗ Problem Statement

بدون تعريف معماري واضح لدور Fake Adapters:

* قد تتحول الـ Fakes إلى ORM وهمي
* قد يتم استخدامها في production بالخطأ
* قد تعطي ثقة زائفة بنتائج الاختبارات
* قد تصبح معقدة أكثر من اللازم
* قد تنحرف عن سلوك المكتبة الحقيقي

نحتاج إلى **ضمانات اختبار واضحة ومحدودة**.

---

## ✅ Decision

### 🎯 Fake Adapters Purpose (Scope Locked)

Fake Adapters موجودة **حصريًا** من أجل:

* Unit testing
* Deterministic behavior
* Offline testing
* CI pipelines بدون خدمات خارجية

❌ ليست بديلًا عن:

* Performance testing
* Load testing
* Integration testing الحقيقي

---

### 1️⃣ **Behavioral Fidelity Only**

Fake Adapters يجب أن تحاكي:

* Contract behavior
* Input / Output semantics
* Error cases المتوقعة
* Repository lifecycle

❌ لا يجب أن تحاكي:

* Performance characteristics
* Memory limits الحقيقية
* Concurrency
* Network latency
* Driver-specific quirks

---

### 2️⃣ **In-Memory Deterministic Storage**

كل Fake Adapter:

* يعمل In-memory فقط
* يستخدم هياكل بيانات بسيطة (arrays, maps)
* يُعيد نفس النتائج دائمًا لنفس المدخلات

أي سلوك non-deterministic مرفوض.

---

### 3️⃣ **Strict Interface Compliance**

Fake Adapters:

* **ملزمة** بتطبيق نفس `AdapterInterface`
* تمر بنفس validation في `BaseRepository::validateAdapter()`
* لا تحتوي على طرق إضافية خاصة بالاختبار

أي Fake لا يمر من نفس الـ Repository code path هو Fake غير صالح.

---

### 4️⃣ **Explicit Capability Limitations**

Fake Adapters:

* لا تدعم كل features (مثلاً: Mongo aggregation, Redis scripts)
* يجب أن:

    * ترمي Exceptions واضحة عند عدم الدعم
    * أو توثّق بوضوح ما هو المدعوم وما هو غير المدعوم

❌ ممنوع:

* Silent fallback
* نتائج ناقصة بدون تحذير

---

### 5️⃣ **No Production Usage Guarantee**

يجب أن يكون هناك:

* Namespace واضح (`DataFakes`, `Fake*Adapter`)
* Documentation صريحة تمنع استخدامها في production
* (اختياري) Runtime assertion أو marker class لمنع misuse

أي استخدام للـ Fake Adapter خارج بيئة الاختبار يُعتبر خطأ تصميمي من المستهلك.

---

### 6️⃣ **Testing Guarantees Provided**

باستخدام Fake Adapters، المكتبة **تضمن**:

* Repository logic correctness
* Hydration correctness
* Filtering & ordering correctness (ضمن الحدود المعلنة)
* Pagination logic correctness
* Error handling paths

❌ لا تضمن:

* Query performance
* Driver edge cases
* Locking / race conditions

---

### 7️⃣ **No Divergence Rule**

أي تغيير في:

* Repository behavior
* Filter semantics
* Hydration lifecycle

يجب أن ينعكس **فوريًا** في:

* Fake Adapters
* Associated tests

أي divergence بين real adapters و fakes هو **bug**.

---

## ❌ Explicitly Rejected Alternatives

تم رفض ما يلي:

* Mocking repositories بدل adapters
* Using PHPUnit mocks بدل Fake Adapters
* Using Fakes as lightweight ORM
* Benchmarking against fakes
* Environment-based adapter switching

هذه الأساليب تُضعف الثقة في الاختبارات.

---

## 🏁 Consequences

### ✅ Positive

* Tests سريعة ومستقرة
* CI بدون خدمات خارجية
* سلوك متوقع
* Isolation ممتاز للـ repository logic
* Debugging أسهل

### ⚠️ Trade-offs

* لا تغطي الأداء الحقيقي
* لا تحاكي كل driver features
* تحتاج صيانة متزامنة مع core logic

هذه التضحيات **مقصودة ومقبولة**.

---

## 📌 Final Note

Fake Adapters في `maatify/data-repository`:

* **أداة اختبار**
* **ليست بديلاً عن الواقع**
* **مقفولة النطاق**
* **ملزمة بالعقود**

أي توسعة مستقبلية يجب أن تحترم هذا الدور أو تنتقل لمكتبة Testing منفصلة.
