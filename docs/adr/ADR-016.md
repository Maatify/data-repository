# ADR-016: Repository Contract Boundary

## Status
Accepted

## Context
The project contains concrete repository implementations that expose methods
not declared in `RepositoryInterface` (e.g. pagination, count, convenience helpers).

This created ambiguity regarding:
- What constitutes a public, stable API
- Whether such methods are safe to rely upon
- How Redis capability limitations should influence contracts

## Decision
Only methods explicitly declared in `RepositoryInterface` are considered **contractual**.

Any method that:
- Exists only in concrete implementations, and
- Is not declared in the interface

is classified as **Non-Contractual Convenience Behavior**.

Such methods:
- MUST NOT be relied upon by consumers
- MUST NOT be added to interfaces in v1.x
- MAY be removed, changed, or limited per driver without breaking guarantees

Redis defines the **minimum capability baseline** for all repository contracts.

No repository may throw runtime exceptions for contractual methods due to driver limitations.

## Consequences
### Positive
- Clear, enforceable public API boundary
- Strong backward compatibility guarantees
- Redis safety constraints preserved
- Enables safe future refactoring

### Negative
- Some useful methods remain undocumented at contract level
- Interface segregation must be postponed to v2.0

## Future Direction
Interface segregation (`ReadRepositoryInterface`, `WriteRepositoryInterface`)
is explicitly deferred to **v2.0**, where breaking changes are permitted.
