## 🧠 Context

`maatify/data-repository` يعمل كطبقة Infrastructure حرِجة، حيث الأخطاء ليست مجرد حالات فشل عادية، بل **إشارات تعاقدية** يجب أن تكون:

* واضحة
* قابلة للتصنيف
* متوقعة
* قابلة للتحليل الثابت والاختبار

تعدد مصادر الأخطاء (Adapters، Filters، Hydration، Pagination، Redis Guards) يتطلب **نظام تصنيف Exceptions موحّد** يمنع:

* الرسائل العامة المبهمة
* catch-all patterns
* فقدان السياق
* اختلاف السلوك حسب التخزين

---

## ❗ Problem Statement

بدون Taxonomy واضحة للأخطاء:

* يصعب التمييز بين أخطاء الاستخدام وأخطاء البنية
* يضطر المستهلك لعمل `catch (\Throwable)`
* تفشل الاختبارات في التحقق من مسارات الخطأ
* تتسرّب تفاصيل Driver خارج حدود المكتبة
* يصبح التعامل مع Redis / Mongo / MySQL غير متسق

نحتاج إلى **نظام Exceptions هرمي ومغلق**.

---

## ✅ Decision

### 1️⃣ **Root Exception Is Mandatory**

كل Exceptions في المكتبة **يجب** أن ترث من:

```
Maatify\DataRepository\Exception\RepositoryException
```

❌ ممنوع:

* رمي Exceptions خام من PDO / Mongo / Redis
* رمي `\RuntimeException` مباشرة
* رمي `\LogicException` بدون تغليف

---

### 2️⃣ **Exception Categories (Taxonomy)**

يتم تقسيم الأخطاء إلى الفئات التالية (غير قابلة للتغيير):

#### 🔹 Configuration Exceptions

أخطاء إعداد أو wiring:

* Adapter غير متوافق
* Repository misconfiguration
* Missing dependencies

**مثال:**

* `InvalidAdapterException`
* `RepositoryConfigurationException`

---

#### 🔹 Query / Operation Exceptions

أخطاء أثناء تنفيذ العمليات:

* SQL execution failures
* Mongo query failures
* Redis command failures

**مثال:**

* `QueryExecutionException`
* `DriverOperationException`

> يجب تغليف أي Driver exception مع الاحتفاظ بالـ cause.

---

#### 🔹 Validation Exceptions

أخطاء مدخلات أو invariants:

* Filters غير صالحة
* Limit / offset خارج النطاق
* Ordering غير مدعوم

**مثال:**

* `InvalidFilterException`
* `InvalidPaginationException`

---

#### 🔹 Hydration Exceptions

أخطاء أثناء الـ Hydration lifecycle:

* Casting failures
* Validation stage failures
* Mapping errors

**مثال:**

* `HydrationException`
* `HydrationValidationException`

---

#### 🔹 Safety & Guard Exceptions

أخطاء ناتجة عن تجاوز حدود الأمان:

* Redis safety limits
* Unsafe operations
* Forbidden behaviors

**مثال:**

* `UnsafeOperationException`
* `RedisSafetyLimitExceededException`

---

### 3️⃣ **Semantic Meaning Over Message Text**

النوع (Class) هو **العقد الأساسي**، وليس نص الرسالة.

* الرسائل تُستخدم للتشخيص فقط
* لا يُبنى منطق على نص exception
* الاختبارات تعتمد على النوع

---

### 4️⃣ **No Silent Fallbacks**

عند حدوث خطأ:

* ❌ لا silent ignore
* ❌ لا return empty results
* ❌ لا implicit retry

إما:

* نجاح واضح
* أو Exception واضحة من taxonomy

---

### 5️⃣ **Preserve Root Cause (Chaining)**

عند تغليف exceptions:

* يجب تمرير الـ original exception كـ `previous`
* بدون تسريب تفاصيل driver في الرسالة العامة
* التفاصيل الكاملة متاحة عبر chaining فقط

---

### 6️⃣ **Checked-by-Design (Documented Throws)**

كل public method يجب أن:

* يوثّق Exceptions الممكنة في PHPDoc
* لا يرمي Exceptions غير موثّقة

هذا شرط أساسي للتحليل الثابت والـ DX.

---

### 7️⃣ **Testing Guarantees**

الاختبارات يجب أن:

* تتحقق من نوع exception
* تغطي مسارات الفشل الحرجة
* تختبر Redis guards و hydration failures صراحة

أي مسار فشل غير مُختبَر يُعتبر **نقص تغطية**.

---

## 🔧 Mandatory Implementation Requirements

هذا الـ ADR يفرض:

1. إنشاء hierarchy واضح للـ Exceptions
2. منع تسريب Driver exceptions
3. توحيد exception types عبر كل storages
4. توثيق throws لكل public API
5. إضافة اختبارات لمسارات الخطأ

---

## ❌ Explicitly Rejected Alternatives

تم رفض ما يلي:

* Generic `RuntimeException`
* Exception messages كـ API
* Silent error handling
* Storage-specific exception exposure
* Catch-all patterns داخل المكتبة

هذه الأساليب تُضعف الثقة والتحكم.

---

## 🏁 Consequences

### ✅ Positive

* Error handling واضح ومتوقع
* اختبارات أدق
* DX أفضل
* Debugging أسهل
* Static analysis أقوى

### ⚠️ Trade-offs

* عدد Exceptions أكبر
* Boilerplate إضافي
* انضباط أعلى مطلوب

هذه التضحيات **مقصودة ومقبولة**.

---

## 📌 Final Note

Exception handling في `maatify/data-repository`:

* **Taxonomy مقفولة**
* **Hierarchical**
* **Type-driven**
* **Non-silent**
* **Infrastructure-safe**

هذا القرار **مغلق** لكل إصدارات v1.x.
