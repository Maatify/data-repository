## 🧠 Context

`GenericMongoRepository` provides convenience behavior by automatically converting 24-character hexadecimal strings into `MongoDB\BSON\ObjectId` instances when querying by identifier.

While this behavior improves developer experience in common cases, it introduces **implicit magic** that may cause ambiguous or incorrect queries when:

* A document legitimately uses a string ID that matches the ObjectId pattern
* Consumers expect literal string matching
* Debugging relies on predictable, explicit behavior

Given the library’s strict design philosophy, ObjectId casting rules must be **explicit, predictable, and documented**.

---

## ❗ Problem Statement

Implicit ObjectId casting can cause:

* Unexpected “record not found” results
* Inability to query literal string values that resemble ObjectIds
* Hidden behavior that violates the principle of least surprise
* Difficulty reasoning about query semantics during debugging

A clear, enforceable policy is required to balance convenience and correctness.

---

## ✅ Decision

### 1️⃣ **Explicit Casting Rules Are Defined**

Automatic casting to `ObjectId` is allowed **only** under strict, well-defined conditions.

A value **may be cast** to `ObjectId` if:

* It is explicitly intended to represent a MongoDB `_id`
* It is a valid 24-character hexadecimal string
* The query context is identifier-based (e.g. `find(id)`)

Automatic casting **must not** occur in arbitrary filter contexts by default.

---

### 2️⃣ **`find(id)` Allows Controlled Casting**

For `find(id)` operations:

* If the provided `$id` is:

    * A `MongoDB\BSON\ObjectId` → use as-is
    * A valid 24-character hex string → cast to `ObjectId`
* No other fields are subject to implicit casting

This preserves the common and expected MongoDB usage pattern.

---

### 3️⃣ **`findBy()` Does NOT Implicitly Cast Arbitrary Fields**

For filter-based queries (`findBy`, `paginate`):

* No automatic casting is performed on filter values
* All values are treated as literal unless explicitly provided as `ObjectId`
* Consumers must pass `new ObjectId(...)` manually when required

This prevents accidental misinterpretation of string values.

---

### 4️⃣ **Explicit Opt-In for Advanced Casting (Optional)**

If advanced casting is required, it must be:

* Explicitly opt-in
* Clearly named
* Documented

Example (conceptual):

```php
$repo->findBy([
    '_id' => MongoId::fromString($id)
]);
```

Implicit magic beyond this is forbidden.

---

### 5️⃣ **Documentation Is Mandatory**

The casting behavior must be clearly documented:

* In README
* In Mongo-specific repository docs
* In method-level PHPDoc where casting occurs

Consumers must not “discover” this behavior accidentally.

---

## 🔧 Mandatory Implementation Requirements

This ADR mandates:

1. Restrict ObjectId casting to `find(id)` only
2. Remove implicit casting from generic filter parsing
3. Require explicit `ObjectId` instances for non-ID fields
4. Add regression tests for:

    * Literal string IDs
    * ObjectId casting behavior
5. Document casting rules clearly

---

## ❌ Explicitly Rejected Alternatives

The following approaches are rejected:

* Casting any 24-char hex string automatically in filters
* Heuristic-based detection without context
* Silent fallback behavior
* Mixed implicit/explicit casting rules

All rejected approaches introduce ambiguity.

---

## 🏁 Consequences

### Positive

* Predictable MongoDB query behavior
* No accidental mis-casting
* Easier debugging
* Stronger principle-of-least-surprise compliance

### Trade-offs

* Slightly more verbosity for advanced Mongo usage
* Consumers must be explicit in some cases

These trade-offs are **intentional and acceptable**.

---

## 📌 Final Note

This ADR **locks MongoDB ObjectId casting behavior** for `maatify/data-repository` v1.x.

Any future changes must:

* Preserve explicitness
* Avoid hidden magic
* Respect developer intent
