## 🧠 Context

`maatify/data-repository` يعتمد على **Hydration Pipeline** متعددة المراحل لتحويل البيانات الخام (arrays) إلى كائنات Domain Objects.

النظام الحالي ليس مجرد Mapper بسيط، بل Lifecycle واضح ومقصود:

```
Prepare → Cast → Map → Validate → Complete
```

ظهرت اقتراحات (في بعض التقارير) لتبسيط هذا النظام أو استبداله بـ:

* constructor promotion
* attributes
* reflection-based mappers
* auto-casting المباشر

لكن هذه الاقتراحات **تتعارض** مع أهداف المكتبة طويلة المدى.

---

## ❗ Problem Statement

بدون عقد (Contract) واضح ومقفول للـ Hydration:

* سيظهر سلوك غير متوقع أثناء التحويل
* قد يتم إدخال منطق Domain في Repository
* ستفقد المكتبة قدرتها على:

    * validation المرحلي
    * التحويل الشرطي
    * التحكم في lifecycle
* سيصبح من الصعب ضمان type safety وdeterminism

نحتاج إلى **تعريف رسمي غير قابل للكسر** لما يعنيه “Hydration” داخل هذه المكتبة.

---

## ✅ Decision

### 🔒 Hydration Lifecycle is a **Locked Contract**

نظام الـ Hydration الحالي هو **جزء أساسي من هوية المكتبة**
ويُعتبر **Contract معماري غير قابل للتغيير**.

أي Repository أو Hydrator داخل المكتبة **ملزم** باتباع هذا الـ lifecycle.

---

### 1️⃣ **Mandatory Stages (Non-Optional)**

كل عملية Hydration تمر بالترتيب التالي، بدون تخطي افتراضي:

1. **Prepare**

    * Normalize keys
    * Clean raw values
    * Pre-transform input shape

2. **Cast**

    * Primitive casting (int, float, bool, datetime, json)
    * No domain logic allowed

3. **Map**

    * Assign values to object
    * Apply mapping profiles
    * Apply transformers

4. **Validate**

    * Domain-level consistency checks
    * Throw explicit exceptions on failure

5. **Complete**

    * Final hooks
    * Post-hydration invariants

الترتيب **إجباري** ولا يجوز تغييره.

---

### 2️⃣ **Explicit Control via HydrationContext**

التحكم في المراحل يتم فقط عبر `HydrationContext`:

* تحديد stages
* تمرير metadata
* اختيار MappingProfile

❌ ممنوع:

* global flags
* static toggles
* environment-based behavior

---

### 3️⃣ **No Implicit Magic**

Hydration **must never rely on**:

* Reflection-based auto mapping
* Attribute-driven implicit wiring
* Constructor guessing
* Silent field dropping

كل تحويل يجب أن يكون:

* Explicit
* Predictable
* Testable

---

### 4️⃣ **Hydration Is NOT Serialization**

Hydration داخل هذه المكتبة:

* ليست ORM
* ليست Serializer
* ليست DTO mapper تلقائي

هي **Controlled Object Construction Pipeline**
وليست اختصارًا للكود.

---

### 5️⃣ **Type Safety is Mandatory**

* `hydrate()` يجب أن يُرجع `T`
* `hydrateAll()` يجب أن يُرجع `array<T>`
* أي fallback (مثل `stdClass`) هو:

    * مسموح فقط بدون Hydrator
    * ومُعتبر حالة downgrade واضحة

---

### 6️⃣ **Performance Trade-off is Accepted**

تم قبول أن Hydration متعددة المراحل:

* أبطأ من casting المباشر
* أكثر verbose
* أكثر تكلفة حسابيًا

لكن هذا **قرار واعي** مقابل:

* Domain correctness
* Debuggability
* Deterministic behavior
* Enterprise safety

---

## ❌ Explicitly Rejected Alternatives

تم رفض ما يلي بشكل صريح:

* Attribute-based hydration
* Constructor-only hydration
* Reflection-driven auto mapping
* ORM-style lazy loading
* Magic field inference

هذه الأساليب:

* تقلل السيطرة
* تُخفي الأخطاء
* لا تناسب مكتبة بنطاق Infrastructure

---

## 🏁 Consequences

### ✅ Positive

* Lifecycle واضح ومقروء
* Domain rules enforced consistently
* Debugging أسهل
* Static analysis أقوى
* Behavior ثابت عبر كل repositories

### ⚠️ Trade-offs

* Boilerplate أكثر
* Learning curve أعلى
* Performance أقل من الحلول السريعة

هذه التضحيات **مقبولة ومقصودة**.

---

## 📌 Final Note

Hydration Lifecycle في `maatify/data-repository`:

* **Contract معماري**
* **غير قابل للتبسيط أو الاستبدال**
* **ثابت عبر كل الإصدارات 1.x**

أي تحسين مستقبلي يجب أن:

* يحترم هذا الـ lifecycle
* أو يُقدَّم كمكتبة منفصلة تمامًا
