## 🧠 Context

Redis repositories in `maatify/data-repository` are intentionally scoped as **key-value / cache-oriented** abstractions.
Despite this scope, runtime misuse (large keyspaces, unbounded scans, in-memory filtering) can still occur if not actively prevented.

Static documentation alone is insufficient to guarantee safe Redis usage.
Therefore, **runtime safety limits and guards** are required to enforce correct behavior under real workloads.

---

## ❗ Problem Statement

Without enforced runtime limits, Redis repositories may:

* Trigger blocking behavior or excessive SCAN loops
* Exhaust PHP memory during in-memory filtering
* Cause unpredictable latency spikes
* Fail silently under large datasets
* Be misused as relational/queryable stores

A **hard, enforceable safety model** is required to protect production systems.

---

## ✅ Decision

### 1️⃣ **Mandatory Hard Limits**

Redis repositories **must enforce** a maximum number of items that can be processed in memory during a single operation.

* Default hard limit: **5,000 items**
* The limit must be:

    * Configurable
    * Enforced at runtime
    * Documented

Operations exceeding this limit **must not continue silently**.

---

### 2️⃣ **SCAN-Based Iteration Only**

All Redis key enumeration **must** use:

* `SCAN` with a cursor
* Configurable batch size

Forbidden behaviors:

* `KEYS`
* Full keyspace enumeration without limits
* Single-pass full scans

---

### 3️⃣ **Runtime Guards for Unsafe Operations**

The following operations require runtime guards:

* `findAll()`
* `findBy()`
* `paginateBy()`

Guards must:

* Track the number of items processed
* Abort execution when limits are exceeded
* Trigger one of:

    * A descriptive exception
    * A clearly logged warning + early exit

Silent continuation is forbidden.

---

### 4️⃣ **Fail-Fast Principle**

Redis repositories must follow **fail-fast behavior**:

* Unsafe operations must stop immediately
* Errors must be explicit and descriptive
* No partial or misleading results are allowed

Example error intent:

> Redis filtering aborted: dataset exceeds configured safety limit (5000 items)

---

### 5️⃣ **Explicit Configuration Surface**

Safety limits must be configurable via:

* Constructor parameters **or**
* Explicit configuration objects

Implicit environment-based configuration is forbidden.

Defaults must be safe by design.

---

### 6️⃣ **Documentation & Visibility**

All safety limits and guards must be:

* Documented in README
* Referenced in Redis-specific docs
* Mentioned in method-level PHPDoc where applicable

Consumers must be aware of these constraints **before runtime**.

---

## 🔧 Mandatory Implementation Requirements

This ADR mandates:

1. Introduction of a Redis safety limit constant/config
2. Runtime counters during SCAN-based iteration
3. Guard checks for all Redis read operations
4. Explicit failure paths when limits are exceeded
5. Tests validating guard behavior under large datasets

---

## ❌ Explicitly Rejected Alternatives

The following are rejected:

* Silent truncation of results
* Unlimited Redis scans
* Trusting consumers to “know better”
* Environment-variable–only configuration
* Redis-as-relational emulation

These approaches undermine safety guarantees.

---

## 🏁 Consequences

### Positive

* Prevents production outages
* Eliminates OOM risks
* Enforces correct Redis usage patterns
* Makes Redis behavior predictable
* Aligns runtime behavior with documented scope

### Trade-offs

* Reduced flexibility for large Redis datasets
* Additional configuration surface
* Possible breaking behavior for previously unsafe usage

These trade-offs are **intentional and accepted**.

---

## 📌 Final Note

This ADR **locks Redis safety enforcement** for `maatify/data-repository` v1.x.

All Redis repositories **must** comply with these runtime limits and guards.
