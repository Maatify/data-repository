# 📜 Architecture Decision Record (ADR)

## ADR-002 — Redis Repository Behavior & Safety Constraints

**Status:** ✅ Accepted
**Date:** 2025-12-19
**Project:** `maatify/data-repository`
**Decision Owner:** Maatify Architecture
**Related ADRs:**

* ADR-001 — DataRepository Scope Lock & Refinement Strategy

---

## 🧠 Context

`Maatify DataRepository` provides a unified repository abstraction across MySQL, MongoDB, and Redis.

Unlike relational and document databases, **Redis is a key-value in-memory data store** with fundamentally different characteristics:

* No native query language
* Blocking commands (`KEYS *`) are unsafe at scale
* Filtering and pagination are not first-class operations
* Data access patterns must be explicitly constrained

Multiple expert reviews identified Redis usage as the **single highest operational risk** if left unconstrained or undocumented.

---

## ❗ Problem Statement

Treating Redis as a relational or document store leads to:

* Blocking operations that stall Redis entirely
* Unbounded memory usage in PHP (OOM crashes)
* Misleading API symmetry with MySQL/Mongo
* Unsafe production behavior on large datasets
* Incorrect assumptions by library consumers

A **strict, enforceable Redis behavior model** is required.

---

## ✅ Decision

### 1️⃣ **Redis Is Explicitly Non-Relational**

Redis repositories are defined as:

* **Key-value / cache-oriented**
* Optimized for **direct access by key**
* Suitable for **small or pre-indexed datasets only**

Redis repositories are **NOT**:

* Query engines
* Relational abstractions
* Document stores
* Drop-in replacements for MySQL/Mongo repositories

---

### 2️⃣ **Blocking Commands Are Forbidden**

The following Redis commands are **explicitly banned** in this library:

* `KEYS`
* Any operation that enumerates all keys without iteration

**Mandatory replacement:**

* `SCAN` (cursor-based, non-blocking iteration)

---

### 3️⃣ **In-Memory Filtering Is Guarded**

Redis `findBy()` and similar operations:

* MAY perform in-memory filtering **only** when:

    * Dataset size is explicitly limited
    * A hard upper bound is enforced

**Mandatory safeguards:**

* Default hard limit (e.g. 5,000 items)
* Configurable batch size for SCAN
* Runtime guard:

    * Warning **or**
    * Exception when unsafe usage is detected

Silent full-dataset filtering is **forbidden**.

---

### 4️⃣ **Pagination Has Explicit Constraints**

Redis pagination:

* Is implemented via slicing of a bounded result set
* Must never operate on an unbounded dataset
* Must fail fast if limits are exceeded

Redis pagination is **best-effort**, not guaranteed to scale.

---

### 5️⃣ **No API Symmetry Promise**

The repository API may be **structurally similar**, but **behavioral symmetry is explicitly rejected**:

* MySQL/Mongo provide server-side filtering
* Redis does not

Consumers **must not assume** equivalent performance or capabilities.

This asymmetry is **intentional and documented**.

---

### 6️⃣ **Naming & Documentation Clarity**

Redis repositories must be documented and/or named to reflect their nature:

* Key-value access
* Cache-like behavior
* Explicit limitations

Example documentation language:

> Redis repositories are intended for cache-style or indexed access patterns.
> They are not designed for arbitrary querying.

---

## 🔧 Mandatory Implementation Requirements

This ADR mandates the following changes:

1. Replace all `KEYS *` usage with `SCAN`
2. Introduce hard limits on Redis filtering
3. Add runtime guards for unsafe operations
4. Explicitly document Redis constraints in README / SCOPE
5. Add safety-focused tests for Redis behavior

---

## ❌ Explicitly Rejected Approaches

The following are **explicitly rejected**:

* Redis-based query engines
* Redis relational emulation
* Redis joins or aggregations
* Redis pagination over unbounded datasets
* Silent fallback to full dataset scans

Any of the above requires a **separate library with a different scope**.

---

## 🏁 Consequences

### Positive

* Prevents Redis misuse in production
* Eliminates blocking behavior
* Protects PHP processes from OOM
* Sets correct expectations for users
* Keeps library honest and safe

### Trade-offs

* Reduced Redis feature parity
* Explicit limitations on filtering/pagination
* More responsibility on the consumer to design data models correctly

These trade-offs are **intentional and accepted**.

---

## 📌 Final Note

This ADR **locks Redis behavior permanently** for `maatify/data-repository` v1.x.

Any future Redis enhancements must:

* Respect this behavior model
* Remain explicitly opt-in
* Never violate safety guarantees
