## 🧠 Context

`maatify/data-repository` يقدّم نتائج Pagination عبر **DTOs صريحة** بدل arrays غير منضبطة.
هذا القرار مرتبط مباشرةً بأهداف المكتبة الأساسية:

* Type safety
* Deterministic behavior
* Static analysis (PHPStan Level Max)
* API contracts واضحة لا تتغير بسياق الاستخدام

ظهرت اقتراحات لاستبدال الـ DTOs بـ:

* arrays مرنة
* generators
* lazy collections
* ORM-like paginators

لكن هذه البدائل تُضعف الضمانات المعمارية المطلوبة.

---

## ❗ Problem Statement

بدون عقد Pagination صارم:

* المستهلك لا يعرف ما الذي يمكن الاعتماد عليه
* تظهر اختلافات بين MySQL / Mongo / Redis
* يصبح من الصعب اختبار السلوك
* يضعف التحليل الثابت
* تتسرّب assumptions غير صحيحة عن النتائج

نحتاج إلى **Pagination Contract ثابت ومضمون**.

---

## ✅ Decision

### 1️⃣ **Pagination Returns DTOs Only**

كل عمليات Pagination **يجب** أن تُرجع DTO صريحًا:

* `PaginationResultDTO` (أو ما يكافئه)

❌ ممنوع:

* إرجاع arrays
* إرجاع collections بدون عقد
* mixed return types

---

### 2️⃣ **Mandatory Pagination Result Structure**

كل Pagination DTO **يجب** أن يحتوي على:

* `items` → `array<T>` (Hydrated objects أو raw arrays حسب السياق)
* `total` → `int` (إجمالي العناصر قبل pagination)
* `page` → `int`
* `perPage` → `int`
* `pages` → `int` (محسوبة، وليست اختيارية)

كل الحقول **إجبارية وغير nullable**.

---

### 3️⃣ **Deterministic Guarantees**

Pagination DTO تضمن:

* `count(items) <= perPage`
* `page >= 1`
* `perPage > 0`
* `pages = ceil(total / perPage)`
* `total >= count(items)`

أي خرق لهذه القواعد يُعتبر **bug**.

---

### 4️⃣ **No Lazy or Deferred Evaluation**

Pagination results:

* تُحسب بالكامل قبل الإرجاع
* لا تحتوي على lazy loaders
* لا تعتمد على generators
* لا تُنفّذ queries مؤجلة

الهدف:

* نتائج قابلة للاختبار
* سلوك متوقع
* عدم وجود side effects بعد الإرجاع

---

### 5️⃣ **Storage-Agnostic Contract**

رغم اختلاف آليات التنفيذ:

* MySQL → `COUNT(*)`
* MongoDB → `countDocuments`
* Redis → bounded scan + count (ضمن القيود)

إلا أن **الـ DTO النهائي يجب أن يكون متطابقًا** من حيث العقد.

❌ لا يُسمح باختلاف semantics حسب الـ storage.

---

### 6️⃣ **Redis-Specific Constraints Apply**

بالنسبة لـ Redis:

* `total` يعكس عدد العناصر ضمن **النطاق المسموح فقط**
* Pagination تفشل إذا تجاوزت حدود الأمان (ADR-006)
* لا توجد وعود بدقة total خارج النطاق الآمن

هذا السلوك:

* صريح
* موثّق
* مقصود

---

### 7️⃣ **Type Safety Is Mandatory**

* `PaginationResultDTO<T>`
* `items` typed as `array<T>`
* لا `mixed`
* لا casts ضمنية

أي downgrade في النوع يجب أن يكون:

* Explicit
* موثّق
* Opt-in فقط

---

## 🔧 Mandatory Implementation Requirements

هذا الـ ADR يفرض:

1. استخدام Pagination DTO موحّد في كل repositories
2. منع أي إرجاع بديل للـ DTO
3. توحيد حساب `pages`
4. إضافة اختبارات تحقق invariants
5. توثيق فروق Redis بوضوح

---

## ❌ Explicitly Rejected Alternatives

تم رفض ما يلي:

* Returning arrays
* Lazy pagination
* Generator-based results
* ORM-style paginator objects
* Storage-specific pagination contracts

هذه البدائل تُضعف الضمانات وتكسر التوقعات.

---

## 🏁 Consequences

### ✅ Positive

* API ثابت ومتوقع
* Type safety قوية
* Static analysis ممتاز
* اختبارات أبسط
* توحيد سلوك MySQL / Mongo / Redis

### ⚠️ Trade-offs

* مرونة أقل
* بعض overhead في الحساب
* Redis pagination محدودة عمدًا

هذه التضحيات **مقصودة ومقبولة**.

---

## 📌 Final Note

Pagination في `maatify/data-repository`:

* **Contract صارم**
* **DTO-based**
* **Deterministic**
* **غير كسول**
* **مستقل عن نوع التخزين**

هذا القرار **مقفول** لكل إصدارات v1.x.
