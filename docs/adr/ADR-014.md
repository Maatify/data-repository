## 🧠 Context

`maatify/data-repository` هي مكتبة Infrastructure تُستخدم كأساس طويل المدى داخل أنظمة إنتاجية.
أي كسر في التوافقية (Backward Compatibility) قد يؤدي إلى:

* أعطال في تطبيقات قائمة
* تكلفة ترحيل مرتفعة
* فقدان الثقة في المكتبة
* تقييد التحديثات المستقبلية

في المقابل، غياب سياسة واضحة للإيقاف التدريجي (Deprecation) يؤدي إلى تراكم ديون تقنية وعدم القدرة على التطوير المنضبط.

نحتاج إلى **سياسة رسمية، صريحة، وقابلة للتنفيذ**.

---

## ❗ Problem Statement

بدون سياسة واضحة للتوافقية والإيقاف التدريجي:

* التغييرات الصغيرة قد تكسر سلوكًا قائمًا
* المستخدم لا يعرف متى يجب التحديث
* لا يوجد إطار زمني لإزالة APIs قديمة
* يصعب الحفاظ على استقرار v1.x

---

## ✅ Decision

### 1️⃣ **Semantic Versioning Is Mandatory**

المكتبة تلتزم بـ **Semantic Versioning** بشكل صارم:

* **MAJOR (X.0.0)**: تغييرات كاسرة (Breaking)
* **MINOR (1.X.0)**: ميزات جديدة بدون كسر
* **PATCH (1.X.Y)**: إصلاحات بدون تغيير سلوك

أي انحراف عن هذا المبدأ **مرفوض**.

---

### 2️⃣ **v1.x Is Backward-Compatible by Default**

خلال سلسلة **v1.x**:

* ❌ لا تغييرات كاسرة في الـ public API
* ❌ لا تغيير في semantics المعلنة
* ❌ لا إزالة methods أو interfaces

أي كسر محتمل:

* يُؤجَّل إلى v2.0
* أو يُقدَّم عبر آلية Deprecation رسمية فقط

---

### 3️⃣ **Deprecation Is Explicit & Announced**

أي API سيتم إيقافه تدريجيًا يجب أن:

1. يُعلَّم بـ `@deprecated` في PHPDoc
2. يُوثَّق في `CHANGELOG.md`
3. يُذكر البديل المقترح بوضوح
4. يبقى متاحًا طوال **MAJOR version الحالية**

❌ Deprecation صامتة أو غير موثّقة مرفوضة.

---

### 4️⃣ **Minimum Deprecation Window**

* أي API مُعلَّم كـ deprecated في v1.x:

    * **لا يُزال** قبل v2.0
    * يبقى عاملًا بالكامل
    * لا يتغير سلوكه

التحذير = توجيه، وليس إجبارًا فوريًا.

---

### 5️⃣ **Behavioral Stability Is a Contract**

* Fixes لا يجوز أن:

    * تغيّر semantics
    * تغيّر return types
    * تغيّر error behavior

أي تغيير في السلوك—even لو بدا “تحسينًا”—يُعامل كتغيير كاسر.

---

### 6️⃣ **ADR Decisions Are Compatibility Boundaries**

كل ADR من ADR-001 إلى ADR-014:

* يُعتبر جزءًا من **العقد العام للمكتبة**
* لا يجوز كسره داخل v1.x
* أي تغيير عليه = MAJOR release

---

### 7️⃣ **Deprecation ≠ Removal**

* Deprecation:

    * توثيق
    * تحذير
    * بديل
* Removal:

    * فقط في MAJOR release
    * مع Migration Guide

---

### 8️⃣ **Migration Guides Are Mandatory**

أي MAJOR release (مثل v2.0):

* يجب أن يتضمن:

    * `UPGRADE.md`
    * أمثلة before/after
    * شرح التغييرات الكاسرة
    * خطوات ترحيل واضحة

بدون Migration Guide → release غير مقبول.

---

## 🔧 Mandatory Implementation Requirements

هذا الـ ADR يفرض:

1. الالتزام الصارم بـ SemVer
2. توثيق أي Deprecation فورًا
3. منع التغييرات السلوكية في PATCH/MINOR
4. ربط ADRs كعقد رسمي
5. إضافة سياسة Deprecation في README

---

## ❌ Explicitly Rejected Alternatives

تم رفض ما يلي:

* “Soft breaking changes”
* Silent behavior changes
* Removing APIs without notice
* Treating bug fixes as justification للكسر
* Environment-based feature toggles

هذه الأساليب تُدمّر الثقة والاستقرار.

---

## 🏁 Consequences

### ✅ Positive

* ثقة عالية في التحديثات
* استقرار طويل المدى
* تخطيط أفضل للمستخدمين
* تقليل المخاطر في الإنتاج
* حوكمة واضحة للتغيير

### ⚠️ Trade-offs

* بطء نسبي في التطور
* التزام أعلى بالانضباط
* الحاجة لتخطيط مسبق

هذه التضحيات **مقصودة ومناسبة** لمكتبة Infrastructure.

---

## 📌 Final Note

`maatify/data-repository`:

* تفضّل **الاستقرار** على السرعة
* تحترم المستخدمين الحاليين
* لا تكسر العقود دون إعلان
* تعتمد التدرج لا المفاجأة

هذا القرار **مغلق** لكل إصدارات v1.x.
