## 🧠 Context

`count()` operations are deceptively simple but **semantically critical**.
Across heterogeneous storages (MySQL, MongoDB, Redis), the meaning of “count” can diverge if not explicitly defined and enforced.

Because Pagination (ADR-010) and filtering rely on `count()` correctness, inconsistent semantics introduce subtle bugs, broken UX, and misleading metrics.

---

## ❗ Problem Statement

Without a strict contract for `count()`:

* MySQL may return total rows, while Mongo returns filtered counts
* Redis may not be able to compute a safe count at all
* Pagination metadata becomes unreliable
* Consumers misinterpret results (e.g., assuming global totals)
* Runtime behavior differs silently by storage engine

A **single, enforceable semantic definition** for `count()` is required.

---

## ✅ Decision

### 1️⃣ **`count()` Is Always Filter-Scoped**

`count()` **always** represents:

> The number of records matching the provided filter criteria
> **within the repository’s supported and safe scope**

There is **no concept of “global count”** unless explicitly requested and supported.

---

### 2️⃣ **Explicit Method Contract**

Repositories may expose:

* `count()` → count **without filters**
* `countBy(array $filters)` → count **with filters**

Both methods must follow the **same semantic rules**.

❌ Overloaded or ambiguous `count()` behavior is forbidden.

---

### 3️⃣ **Storage-Specific Execution (Unified Semantics)**

Implementation differs, semantics do not:

* **MySQL** → `SELECT COUNT(*) FROM table WHERE ...`
* **MongoDB** → `countDocuments(filter)`
* **Redis** → bounded SCAN-based count **within safety limits**

Regardless of backend, the returned value **must reflect the same intent**.

---

### 4️⃣ **Redis Has Explicit Count Constraints**

For Redis repositories:

* `count()` and `countBy()` are:

    * Allowed **only** within safety limits (ADR-006)
    * SCAN-based
    * Bounded

If the operation exceeds safety limits:

* The method **must fail fast**
* With a descriptive exception (preferred)

Silent partial counts are **forbidden**.

---

### 5️⃣ **No Side Effects**

`count()` operations:

* Must not mutate state
* Must not cache implicitly
* Must not alter cursors or iterators
* Must not depend on prior read calls

Each invocation is **logically isolated**.

---

### 6️⃣ **Deterministic Guarantees**

For any repository:

* `countBy(filters) >= 0`
* `countBy(filters) >= count(paginated.items)`
* `countBy(filters)` is stable for the same dataset snapshot

Violations are considered **bugs**.

---

### 7️⃣ **Integration with Pagination**

Pagination (ADR-010) relies on `count()`:

* `PaginationResultDTO.total` **must equal** the result of `countBy(filters)`
* No recomputation shortcuts or divergent logic allowed

Count logic must be **shared or delegated**, not duplicated.

---

## 🔧 Mandatory Implementation Requirements

This ADR mandates:

1. Explicit definition of `count()` / `countBy()` semantics in interfaces
2. Unified filter handling between count and read paths
3. Redis count guards aligned with ADR-006
4. Shared logic or utilities for count execution
5. Tests verifying:

    * Consistency with pagination totals
    * Redis failure paths
    * Filter equivalence across storages

---

## ❌ Explicitly Rejected Alternatives

The following are rejected:

* Returning approximate counts silently
* Storage-specific interpretations of count
* Lazy or deferred counting
* Using pagination size as a proxy for count
* Ignoring filters during count

These approaches break trust in results.

---

## 🏁 Consequences

### ✅ Positive

* Reliable pagination metadata
* Predictable analytics
* Unified semantics across storages
* Easier testing and reasoning
* Reduced UX inconsistencies

### ⚠️ Trade-offs

* Redis count may fail for large datasets
* Additional guard logic required
* Slight performance overhead in safe paths

These trade-offs are **intentional and accepted**.

---

## 📌 Final Note

`count()` in `maatify/data-repository`:

* Has **one meaning**
* Is **filter-scoped**
* Is **storage-agnostic in semantics**
* Is **guarded for safety**

This decision is **locked** for all v1.x releases.
