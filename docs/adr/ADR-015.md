## 🧠 Context

`maatify/data-repository` مكتبة **Infrastructure** حساسة، وأي Release غير منضبط قد يؤدي إلى:

* كسر غير مقصود في الإنتاج
* فقدان الثقة في التحديثات
* صعوبة التتبع والمراجعة
* اختلافات بين الكود والـ ADRs

لذلك، نحتاج إلى **عملية إصدار (Release Process)** و**حوكمة (Governance)** واضحة، رسمية، وغير قابلة للتأويل.

---

## ❗ Problem Statement

بدون عملية إصدار محكومة:

* قد يتم دمج تغييرات خارج النطاق
* قد تُنشر إصدارات بدون مراجعة معمارية
* قد تُكسر قرارات ADR بدون وعي
* لا يوجد “gate” يمنع الانحراف

نحتاج إلى **نظام Releases قابل للتدقيق والإنفاذ**.

---

## ✅ Decision

### 1️⃣ **Release Types Are Strictly Defined**

يتم اعتماد الأنواع التالية فقط:

* **PATCH (1.x.Y)**

    * Bug fixes فقط
    * بدون تغيير سلوك
    * بدون API changes

* **MINOR (1.X.0)**

    * إضافات داخل النطاق
    * بدون كسر Backward Compatibility
    * يجب أن تحترم كل ADRs

* **MAJOR (X.0.0)**

    * تغييرات كاسرة فقط
    * تتطلب Migration Guide
    * تتطلب ADR جديدة أو تحديث ADRs قائمة

---

### 2️⃣ **ADR Compliance Is a Release Gate**

أي Release:

* **يجب** أن يكون متوافقًا مع كل ADRs السارية
* أي تغيير خارج ADR:

    * ❌ يُرفض
    * أو يتطلب ADR جديدة **قبل الدمج**

ADRs هي **القانون المعماري الأعلى**.

---

### 3️⃣ **Mandatory Pre-Release Checklist**

لا يُسمح بعمل Release بدون:

* ✅ Tests خضراء (Unit + Safety paths)
* ✅ PHPStan Level Max بدون errors
* ✅ CHANGELOG.md مُحدّث
* ✅ SemVer version bump صحيح
* ✅ لا API مكسورة (في v1.x)

---

### 4️⃣ **CHANGELOG Is Source of Truth**

* كل Release **يجب** أن:

    * يُضاف إلى `CHANGELOG.md`
    * يتبع Keep a Changelog
    * يذكر:

        * Added
        * Changed
        * Fixed
        * Deprecated (إن وُجد)

أي Release بدون Changelog → Release غير صالح.

---

### 5️⃣ **No Direct Push to Main**

* `main` فرع محمي
* ❌ لا push مباشر
* كل تغيير يتم عبر:

    * Pull Request
    * Review معمارية
    * CI pass

---

### 6️⃣ **Release Authority Is Explicit**

* الإصدارات الرسمية:

    * يوقّع عليها Maintainer معتمد
    * لا auto-release بدون مراجعة بشرية

Automation **مسموح**، لكن القرار **بشري**.

---

### 7️⃣ **Governance Scope Is Locked**

حوكمة المكتبة تشمل:

* Scope control
* ADR enforcement
* Release validation
* Deprecation policy

ولا تشمل:

* Feature voting
* Roadmap based on popularity
* Runtime configuration policies

---

### 8️⃣ **Emergency Fix Policy**

في حالات حرجة فقط:

* Patch release سريع
* يلتزم بنفس القواعد
* يوثّق بوضوح كـ “Security / Critical Fix”
* لا يُستخدم كذريعة لتجاوز ADRs

---

## 🔧 Mandatory Implementation Requirements

هذا الـ ADR يفرض:

1. حماية فرع `main`
2. اعتماد Pull Request workflow
3. تفعيل CI كـ merge gate
4. الالتزام بـ CHANGELOG
5. ربط ADRs بعملية Release

---

## ❌ Explicitly Rejected Alternatives

تم رفض ما يلي:

* Ad-hoc releases
* “Just fix it” patches بدون توثيق
* Breaking changes في minor/patch
* Auto-publish بدون review
* Ignoring ADRs for speed

هذه الأساليب تُضعف الثقة وتكسر الحوكمة.

---

## 🏁 Consequences

### ✅ Positive

* Releases مستقرة ومتوقعة
* ثقة عالية في التحديثات
* حوكمة واضحة
* سهولة تتبع القرارات
* قابلية صيانة طويلة المدى

### ⚠️ Trade-offs

* سرعة أقل في الإصدارات
* متطلبات مراجعة أعلى
* انضباط أكبر مطلوب

هذه التضحيات **مقصودة ومناسبة** لمكتبة Infrastructure.

Release Process في `maatify/data-repository`:
