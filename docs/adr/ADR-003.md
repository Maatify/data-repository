# 📜 Architecture Decision Record (ADR)

## ADR-003 — Repository Interface Segregation (Read / Write Contracts)

**Status:** ✅ Accepted
**Date:** 2025-12-19
**Project:** `maatify/data-repository`
**Decision Owner:** Maatify Architecture
**Related ADRs:**

* ADR-001 — DataRepository Scope Lock & Refinement Strategy
* ADR-002 — Redis Repository Behavior & Safety Constraints

---

## 🧠 Context

`Maatify DataRepository` exposes a unified repository abstraction across multiple storage engines.

Historically, repositories exposed a **monolithic contract** combining read and write operations (find, paginate, insert, update, delete). While functional, this design violates the **Interface Segregation Principle (ISP)** and introduces several issues:

* Read-only data sources (views, logs, cache snapshots) are forced to implement mutators
* Implementations must throw “Not Supported” exceptions
* Consumers cannot type-hint intent (read vs write)
* Static analysis cannot enforce operation scope

Given the library’s emphasis on strict typing and static analysis, this contract must be refined.

---

## ❗ Problem Statement

A monolithic repository interface:

* Violates ISP
* Encourages runtime exceptions instead of compile-time safety
* Obscures intent in consuming code
* Prevents read-only repositories from being modeled correctly
* Makes Redis and cache-oriented repositories harder to reason about

The contract must be **segmented without breaking compatibility**.

---

## ✅ Decision

### 1️⃣ **Segregate Repository Interfaces**

The repository contract is split into two explicit interfaces:

#### 🔹 ReadRepositoryInterface

Provides read-only operations:

* `find(id)`
* `findBy(filters, order, limit, offset)`
* `paginate(filters, order, page, perPage)`

This interface **must not** expose any mutator methods.

---

#### 🔹 WriteRepositoryInterface

Provides write operations:

* `insert(data)`
* `update(id, data)`
* `delete(id)`

This interface **must not** expose any read methods.

---

### 2️⃣ **RepositoryInterface Extends Both**

For full CRUD repositories:

```php
interface RepositoryInterface extends
    ReadRepositoryInterface,
    WriteRepositoryInterface
{
}
```

This preserves:

* Backward compatibility
* Familiar API for existing consumers

---

### 3️⃣ **BaseRepository Implements Both by Default**

* `BaseRepository` continues to implement `RepositoryInterface`
* Specialized repositories may implement **only** the interface they support
* No repository may throw “Not Supported” exceptions for contract methods

---

### 4️⃣ **Type-Hinting by Intent Is Encouraged**

Consumers are encouraged to depend on the **narrowest possible contract**:

* Read-only services → `ReadRepositoryInterface`
* Write-only workflows → `WriteRepositoryInterface`
* Full CRUD → `RepositoryInterface`

This enables:

* Better static analysis
* Clearer business intent
* Safer dependency injection

---

### 5️⃣ **Redis Repositories Benefit Explicitly**

This segregation enables Redis repositories to:

* Implement read-only access safely
* Avoid exposing unsupported write semantics
* Enforce cache-style usage without runtime guards

This aligns directly with ADR-002.

---

## 🔧 Mandatory Implementation Requirements

This ADR mandates:

1. Creation of `ReadRepositoryInterface`
2. Creation of `WriteRepositoryInterface`
3. Refactoring `RepositoryInterface` to extend both
4. Updating internal type hints to respect segmentation
5. Removing all “unsupported operation” exceptions

---

## ❌ Explicitly Rejected Alternatives

The following approaches are rejected:

* Keeping a single monolithic interface
* Using runtime exceptions to signal unsupported operations
* Introducing marker interfaces without behavioral guarantees
* Auto-detection of repository capabilities

These approaches undermine static guarantees.

---

## 🏁 Consequences

### Positive

* Full compliance with ISP
* Compile-time safety over runtime errors
* Cleaner DI boundaries
* Better Redis and cache repository modeling
* Clearer API intent

### Trade-offs

* Slight increase in interface count
* Minor refactor for existing implementations

These trade-offs are **minimal and acceptable**.

---

## 📌 Final Note

This ADR **locks the repository contract model** for `maatify/data-repository` v1.x.

All future repository designs must conform to this read/write segregation.
